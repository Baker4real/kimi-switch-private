# Windows 当前账号额度查询 401：引导兜底 + 可选主动续期

当前账号额度查询只读 live 凭证、刻意不续期，而官方 TS 客户端在 Windows 上没有任何刷新锁（`process.platform === "win32"` 直接放弃），`lock_protocol_for_version` 据此返回 `None`；叠加 access token 仅 15 分钟寿命与官方懒刷新（闲置不刷），当前账号在 GUI 里 401 是常态，停泊账号因查询前必轮换而不受影响。2026-08-29 与用户确认修复取方案 C：

1. **保守路打底（必做）**：把"凭证过期型 401"识别为独立失败类别，文案明示"在 Kimi CLI 里发条消息即可恢复；或重新授权"；并把额度查询失败从**额度告急**中解耦（告急只表示用量窗口真实达到阈值）。CONTEXT.md 的告急定义随实现同步改，不提前动文档。
2. **进取路可选（opt-in，默认关）**：Windows 上允许工具对当前账号主动续期 live。安全性依据官方 v0.39.1 实证：凭证每次现读文件无内存缓存；invalid_grant 后睡 100ms 重读，发现 refresh token 已被轮换则直接采纳新凭证——正常竞态有自愈兜底。残余风险仅为窄窗口：工具轮换成功而写回前崩溃/卡顿（约 100ms 量级），恰逢官方在刷则官方墓碑化凭证、需重新登录。故必须原子写回（tmp+rename，沿用现有 swap 写序）、被拒记录指纹并停止重试，开关附带风险说明。
3. **规则 4 修订方向**：「只能复用官方锁协议」放宽为「有官方锁用锁；无锁平台允许依赖官方 100ms 重读采纳机制做主动续期」。AGENTS.md 的措辞改动与进取路实现在同一变更集落地，不先行放宽。

已接受的边界：不实现"仅当官方进程未运行才续期"的进程探测——官方即用即读文件，探测缩不了多少窗口却增加误判面；官方若未来在 Windows 引入锁协议，优先改回复用官方锁并重开本决策。官方墓碑化路径（凭证清空、引导 /login）是对方行为，不在本工具防御范围内。
