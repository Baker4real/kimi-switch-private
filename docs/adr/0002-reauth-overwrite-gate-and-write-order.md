# 按卡重授权：凭证覆盖的身份门与写序

按卡重新授权（issue #3，2026-08-27 实现）复用设备码授权流程，但目标是一张已存在的账号卡，而不是收进新身份。凭证覆盖落在 `FileBlobProvider::replace_account_blob`，两条决策约束它：

1. **身份门在一切写入之前**：先从新凭证解析官方账号 id（与入库同规则：`parse_metadata` → `primary_id` 回退 `label`），与目标卡不一致或无法辨认时直接失败——库存不写、live 不写、不新增卡。授权结果绝不是「照单全收」，它必须证明自己还是这张卡。
2. **写序固定「先库存后 live」**：库存是唯一真本，先落库；仅当该卡是当前账号才原子写 live（tmp+rename）。严禁在任何路径先把旧 live 回灌库存——那会把刚写入的新凭证盖掉；后续切换的 capture-on-leave 只属于正常路径。

已接受的边界（有意不做防御）：库存写新成功而 live 原子写失败时，会留下 store=新/live=旧 的窗口，其后一次切换会把旧 live 回灌、静默撤销新凭证。触发前提是罕见的本地 IO 故障，即时状态安全（旧凭证仍可用、无锁死、错误已上抛告知用户）。修正它需要改变切换的 capture 策略，代价大于收益；若未来要改，先重开本决策。

## 修订（issue #5，2026-08-28）：边界扩录与处置决策

独立复核在原记录的 activate capture-on-leave 之外，确认第二条回灌路径：`raw_blob_for_account`
对活跃账号每次读 blob（查额度/导出）都会顺手把 live 回写 store。即重授权 live 写失败留下
store=新/live=旧 窗口后，不需切换、一次额度查询也会静默撤销新凭证。

处置选方案 C（接受现状 + 显式告知）：
- 触发前提仍是罕见本地 IO 故障，无实际复现报告；
- 方案 A（比较 store/live 拒灌）朴素实现会误拒「官方客户端活跃期间合法刷新、live 领先 store」
  的主场景，且堵不住第二条路径；做对需引入持久化同步标记（schema 变更），暂不为理论窗口引入；
- 方案 B（回滚 store）会丢弃新凭证唯一库存副本，且 refresh token 一次性轮换后回滚存入的可能
  是已作废 token，把可恢复状态变成不可恢复，违反凭证安全最高优先级。

落地约束：live 原子写失败时错误文案必须明示三件事——新凭证已保存在库存、live 仍是旧凭证、
补救是尽快重试重新授权。窗口存在期间对外一律以 live 为准（查询与切换都会回灌），这是已接受
的对外行为，由引擎测试钉住。若未来引入「live 同步待定」标记一次堵住两条回灌路径，先重开本决策。

**修订注记（ADR-0019，spec #185 / #189）**：「窗口期一律以 live 为准」改为「可比较时新者胜，不可
比较时以 live 为准」。两条回灌路径（切换的 capture-on-leave、读取当前账号凭证时的顺手回灌），连同
主动续期的采纳回灌，现在先比两份凭证：refresh token 不同就比过期时刻（access token 的 JWT `exp`
优先，缺失回退 `expires_at`），live 严格较旧就不覆盖库存。重新授权的结果比旧 live 新，窗口期内的
查询与切换因此不再撤销它，切走再切回当前登录文件就拿到新凭证；任一方解析不出过期时刻时维持原行为。
不需要同步标记，也不改存储格式；不做「库存较新时主动修复 live」。身份门、先库存后 live 的写序与
错误文案的三项要求不变，引擎测试改为钉住新行为。本注记只改回灌哪份凭证；「当前账号是谁」仍以
live 为准（ADR-0015 决策 9 的启动一致性自检）。详见 ADR-0019 决策 7。
